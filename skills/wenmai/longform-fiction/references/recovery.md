# 从准确落点恢复工作

用于长任务中断、会话更换、宿主工具变化，或入口说明与实际文件不一致时。普通单章修订只需找到当前正文和作者要求，不必另建运行系统。

## 先找正在做的任务

读作者最新要求，再找项目指定的当前批次入口。当前任务决定优先于旧批次限制；沿用已经给出的授权，不在常规小批收口后反复要求作者重新批准。是否发布、联系读者或改变故事方向，仍按本次实际授权判断。

入口保持简短，指向原有权威记录，而不复制整部历史和多套进度数字。至少能找到本次范围、准确采用稿、待办、真实岗位状态与最近实际检查。项目已有组织就沿用。下面只是入口形态，不是固定目录或必须照抄的数据库：

```json
{
  "task": "修订当前连续单元",
  "run": "work/current-run/",
  "authoritative": {
    "tasks": "work/current-run/registry.json",
    "adopted_versions": "work/current-run/adopted-manifest.json",
    "reading_versions": "work/current-run/current-read-index.json"
  },
  "latest_observation": "work/current-run/control/last-check.json",
  "next_action": "核收已交付任务，再处理尚未获得准确读稿意见的章节"
}
```

沿入口实际打开记录，核批次身份、文件版本及正文。摘要写“已完成”而采用表、读程或工具库存不支持时，定位冲突；不能只取日期较新、数字较大或较好看的那份。旧 README 的数字可能只是历史快照。入口失效就回查实际记录，缺失保持未知，不能按目录名补成已经完成。

## 分开确认稿件与岗位

稿件先辨认正式采用、候选和计划。阅读意见绑定到所读字节；后改的新稿不能继承旧 SHA 的阅读证明。相同字节可以明确复用旧读程，但不能把复用说成再次全文读过。实际还需读什么，由改动和本次交付要求决定。

岗位先对照真实工具库存和已经保存的调用结果，再核完整交付。终态、交付、调度位置回收、工具关闭和正文采用分别记录；宿主没有关闭工具时按[批量契约](batch-revision.md)选用实际可支持的方式，不能补造关闭。仅一条“完成”消息或清单里的布尔值不足以证明回收。旧岗不可接管时保留其原状态与缺口，先排除重复任务，再决定是否需要新尝试。

恢复后给出一个可执行的下一动作：核收哪一岗、补读哪个版本或处理哪个未决项。新任务前检查容量与同章互斥；已交付未核收和仍在运行的任务不能重复派发。工具命令仍在运行时，等其实际终态后再执行依赖写入。

## 完成声明写明范围

按作者要求选择需要完成的事项，分别确认：

- 正文是否写齐，或本次指定的修订范围是否处理齐。
- 当前准确稿是否具有本次所需的章节、连续单元或完卷阅读；必要修后复读是否结束。
- 待采用意见、重要冲突和实际岗位是否已经核收。
- 作者要求的目录、合订本或网页是否与采用稿同步。
- 若另有发布任务，远端提交及实际部署是否核实。

这些状态可以分别完成。本地写齐不等于精修完成，精修完成不等于已经上线；小段校对也无需等待整部作品完卷审读。全书任务的收口另见[整书审读](whole-work-review.md)。

结束或交接时只更新实际变化、未决问题和下一落点，保存最近检查的真实结果。数量可由权威记录计算就不在多个入口手工维护。历史完成证据原样保留，新修订和新发布另立批次，避免用今天的结果改写昨天的事实。
